## 3. 文档末尾指派给 Zheng 的 4 条方案：评估与优先级

Google 文档末尾「这些是可能可行的方案，你们看看如何？… _Assigned to zhengboxuan27@gmail.com_」列出 4 条。结合 4 份压力测试报告，评估如下（**仅为评估，未实施**）：

| 方案 | 结论 | 价值（对应报告） | 前置依赖 / 风险 |
|---|---|---|---|
| **① 强化互动感，避免孤立使用 App** | **建议做，P0 但收敛形态** | 补「零真实用户」与长者可用性；报告1 §4 问 4、报告4 §1 | 只做「问题卡片 → 问题队列 → 长者声音回答」的结构化交互，**不做 feed/点赞/关注**（团队红线）。依赖后端记录 CRUD 与审核流，当前无 → 先补方案 ④ |
| **② 升级地图，让城市变化更有动态感** | **建议做，P1 先做数据层** | 「清拆时钟」是 pitch 开场利器；报告3 §3.4、报告4 §3 | 依赖 `village` / `era_or_year` / `geo_fuzzy` 元数据（方案 ④）；政府公开发展范围与时间表、OSM 底图 license 全部【待验证】，未核实前只做标注「示意」的 mock；保持村级 800m 模糊圈，不下钻个人位置 |
| **③ 问题卡片 / 社交卡 / 故事卡** | **最优先，P0** | 一处改动同时解决三件事：长者不碰手机（报告1/4）、真实采集冷启动（报告4 §1）、音频天然切成 `segment` 并压低人工质检成本（报告1 §3、报告3 §3.2） | 最小形态（8–12 张实体卡 + App 内静态卡）**不需后端**，可立即做；题目须避开征地/产权/在世第三人（报告2 §3.3） |
| **④ 故事细分归类 + LLM 自动匹配 + 义工人工兜底** | **最优先，P0 地基** | 「可信性工程」与 RAG 的共同底座；报告3 §3.2、报告1 §2/§3 | 先出 `segment` 元数据 schema v0.1 + 服务端记录 CRUD / 删除日志；`llm_suggested` 与 `review_status` 必须分离，LLM 输出不得直接成为可公开事实；线上 Gemini 未就绪，需先解决密钥与降级策略 |

**依赖链**（建议实施顺序）：

```
④ 元数据 schema + 服务端记录/删除日志（地基）
   └→ ③ 问题卡片（无需后端，可并行先做）
        └→ ① 问题队列/代际对话（需审核流）
             └→ ② 地图时间维动态层（需公开数据核实 + license）
```

**红线检查**：4 条均不违反团队红线，但各有边界——① 必须停在「问题」这一种交互；② 只能用公开村级数据；④ 的自动结果必须标注「机器猜测，未确认」并有人审兜底；全部方案不得把 role-play demo 数据当真实故事对外展示。

**先修的 3 项合规/诚实债**（报告1/2 一致结论）：consent 文案与实际存储一致、服务端隐私过滤一条路径、撤回删除日志。这三项不修，任何新功能都会放大合规风险。

## 4. 跨模型复测操作指引（未完成部分）

1. 打开 `00_Prompt包_跨模型复测.md`，复制第 8–20 行「共用背景」+ 某一个 Prompt 的完整原文。
2. 粘贴到目标模型（HKBU GenAI API 下各模型 / GPT / Claude / Gemini / DeepSeek），取得**原始输出**，不要润色。
3. 按 `模板_归档格式.md` 新建 `报告X_<模型名>_<角色>.md`，原样粘贴输出。
4. 回填各报告末尾「模型间差异备注」：与新版报告的具体差异、更优点、更差点；同时更新本文件第 1 节的状态表。
5. 严禁把本轮 Hunyuan 输出改写后冒充其他模型结果（团队诚实标注红线）。
6. 复测前建议把第 2 节的事实校正一并贴给目标模型，否则其他模型会基于错误背景作答（例如假定已有 RAG 与服务端隐私过滤）。
