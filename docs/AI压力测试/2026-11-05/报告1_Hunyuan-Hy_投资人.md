## 模型输出全文

### 0. 结论先行

以 2026-11-05 的仓库实际状态，**不通过**投资级 / 决赛级压力测试。团队自认的三条"残酷建议"仍然成立：情怀不是商业模式，API 拼接不是壁垒，把手机塞给 80 岁长者不是产品设计。可演示性（demo 能跑）是唯一强项，但比赛评委问的是"does it solve a real problem, and does it work"，而当前唯一故事是团队角色扮演、问答是客户端字符串匹配、四级隐私只有界面。

我不建议现在按 2.0 的 B2G/B2B 叙事去融资或锁定赛道叙事。建议把未来 6 周定义为"验证期"而非"开发期"，达标线是：1 段真实长者录音 + 1 份真实知情同意 + 1 封机构意向书（LOI）+ 1 张可审计的单条成本表。没有这四件东西，任何市场规模数字都是故事。

### 1. 需求真伪剖析：长者自主使用 App 是伪需求

三条证据，按强度排序：

1. **团队自己已经承认**。背景文件的「评委反馈矩阵」写明「把手机塞给 80 岁长者更不是合格的产品设计」，应对方案是「青年志愿者/社工 + 长者双人协同对谈」。既然采录环节已改为双人协同，那么"长者自主使用"就不该再出现在用户画像里。
2. **产品界面与长者能力不匹配**。390px 移动优先、Leaflet 地图、录音抽屉五步流程、四级隐私选择、Q&A 卡片——这些是为志愿者/研究者设计的控件，不是为视力与认知衰退的 75 岁+ 长者设计的。
3. **零真实用户**。仓库中唯一故事 YL-001 带 `rolePlayed: true`，UI 已诚实标注「角色扮演示範故事」；`docs/audit/2026-11-03/zheng-nov-03-audit.md` 确认无真实长者参与。demo 数据不能反推需求。

因此正确的用户/客户拆分是：**讲述者 = 长者（被服务者，不操作 App）；操作者 = 青年志愿者/社工/NGO；付费者 = 需要向监管与公众交代社区影响记录的机构；受益者 = 公众与档案机构**。产品定位应从「长者 App」改为「高效率采录 + 可溯源数字化呈交工具」，这与文档「从转录工具到城市记忆基础设施」的重构方向一致。

**刚性买单意愿怎么证明**：必须走完四步链条，缺一步都只是假设——
① 找出机构「必须做」的条款或披露义务（收地项目的社会影响评估、文物影响评估、ESG 报告的社区文化章节）→ ② 找到对应预算科目与采购主体 → ③ 走通采购/资助流程 → ④ 拿到试点 PO 或 LOI。目前四步全部【待验证】。

**TAM / SAM / SOM 测算逻辑（自下而上，只给公式，不编数字）**

| 层级 | 计算式 | 数据来源（须逐项核实） |
|---|---|---|
| TAM | 全港需社会影响/文物影响评估的收地与市区重建项目数 × 单项目可归属「口述史采集与归档」的预算上限 | 发展局、规划署、市区重建局年报与公开招标文件；CCFS 获批项目清单【待验证】 |
| SAM | 北都范围内未来 3 年动工项目数 × 有社区文化存档披露义务的比例 × 团队可承接份额 | 北都相关公开工程时间表【待验证】；地产商 ESG 报告披露口径【待验证】 |
| SOM | 未来 6 周能取得 LOI / 试用承诺的机构数 × 试点单价 | 团队已接触名单（文档列出信义会、明爱、长春社、关爱队等，但未见书面意向）【待验证】 |

三条纪律：每个乘数必须标来源与核实人（Douglas）；没有来源的数字一律写【待验证】；SOM 只用「已签字或已回邮件」的机构，不用「打算联系」的机构。附带说明：比赛奖金与资助（含文档提及的 HKSTP Ideation 最高 HK$100,000 种子资助）是 runway，不是收入，不能计入 ARR。

### 2. 护城河审查：现状比「API 拼接」更薄

**技术脆弱点（按被追问的概率排序）**

1. 供应商锁定与价格：Google STT `yue-Hant-HK` + Gemini 均为外部商用接口，模型、价格、可用区域、条款都不由团队控制；一旦停用或涨价，核心链路即断。
2. 结构化输出不可验证：`formal_text` / `qa_list` 由 LLM 生成，虽有防幻觉 Prompt，但仓库没有黄金标准集，也没有 WER / 时间戳误差 / 事实一致性的量化口径，「严禁编造」目前是提示词约束而非工程保证。
3. 问答不是 RAG：实际路由是 `POST /api/process`（背景写 `/transcribe` 已不符），前端 `KEYWORD_GROUPS` + `retrieveSegments()` 做字符串包含匹配后拼接原文；`docs/audit/2026-11-03/zheng-nov-03-audit.md:38` 已明确「client-side keyword/bigram matching, not vector search」。把它称作 RAG 会在答辩现场被一句追问击穿。
4. 无数据资产：`/api/process` 只做一次性转写、不落盘、不返回记录 id；存储全靠前端 `localStorage`（`vtn-records-v1`），没有服务端 CRUD、没有审核流、没有版本与撤回日志。
5. 方言覆盖：围头话、客家话、蜑家话无 ASR 路径；且 Whisper 会把粤语口语改写成普通话书面语，与「原音/原文保真」红线冲突。
6. 合规债：四级隐私仅 UI 文案 + 「準備中」toast，无服务端过滤；审计还发现 consent 文案承诺「暂不永久储存」与实际 localStorage 持久化不一致。这是投资尽调里的红旗。

**真正可防御的资产（按 6 周内可积累程度排序）**

- **① 真实、带同意授权的方言语料 + held-out 评测集与公开口径**。Boris 已在做 3–5 段内部测试音频与人工黄金转录；把它制度化（WER/CER、词级时间戳误差、粤语口语用字保留率、按说话人/环境杂音分层），就是别人最难复制的数据资产，也是把「demo-scope」升级为「measured」的唯一路径。
- **② 可验证的 grounding 链路**：原音 → 逐词置信度 → 词级时间戳 → 出处索引 → 答案片段 → 审计日志，全链路可回放、可标记「机器猜测，未确认」。这套「可信性工程」是文档竞品调研中认定的市场空白，比「我们用了 Gemini」有说服力得多，也是方法专利 / ITF 研发要素最现实的落点。
- **③ 离线双引擎**：SenseVoice 原生保留粤语口语用字、可端侧部署，适合网络差的村落；既降单一供应商依赖，又支撑「离线田野采集」场景。但须先验证其置信度输出口径能否与 Google STT 对齐【待验证】。
- **④ PDPO 合规工程**：分级同意、撤回即删、脱敏、保留期与删除日志的服务端实现。这不是加分项，是 B2G/B2B 的准入门槛。
- **⑤ 流程设计**：双人协同采录 + 问题卡片 + 人工兜底复核，属于「服务设计 + 数据质量」组合，可写成 SOP 与培训包，形成机构切换成本。

**明确不要做**：为凑专利去做语音克隆/TTS（违反红线，且与 consent-first 品牌冲突）；把「调用了 GenAI」当技术深度；在没有任何自有标注数据前承诺「方言大模型微调」。

**关于 ITF / 专利**：ITF 类资助通常要求本地研发主体、明确的技术不确定性、研发计划与自有 IP 归属【待验证：具体计划条款须查官方指南】。当前代码与 Prompt 包不够，最小可交付是《技术不确定性说明 + 评测协议 + 数据资产清单》，先由 Zheng/Boris 产出，再判断是否申报。

### 3. Unit Economics：能否自负盈亏

**单条音频边际成本**

```
C_unit = (音频秒数 × STT 单价) + (prompt+输出 token × LLM 单价)
       + (人工质检人时 × 时薪) + (同意管理/复核人时 × 时薪)
       + (存储/带宽/转码) + (志愿者招募与培训摊销)
```

**单价侧**：B2G 项目制采购、B2B SaaS/专案年费、B2B2C 高校订阅、C 端家庭订阅，四类客单价与回款周期完全不同，全部【待验证】。

三条判断：

1. **人工质检是变动成本大头，且随音频时长线性增长**。1 小时录音的人工逐字校对可能数十倍于 API 费用。因此文档末尾提案的「1 层 LLM 自动匹配 + 2 层志愿者/义工人工兜底」与「问题卡片降低开放作答长度」，不只是体验优化，而是直接压低 `C_unit` 的毛利杠杆：LLM 先给时间/地点/主题候选，人工只校正低置信项，把「全量校对」变成「抽检 + 例外处理」。
2. **在零真实数据下，任何盈亏平衡数字都是虚构**。正确做法是做一次实测：连续采集 10 条真实音频，逐条记录 API 计时、token、人工分钟数、返工次数，产出可审计的 `cost log`；再代入 `单价 > C_unit + 固定成本 / 年交付量` 求平衡量。
3. **B2G 回款周期与采购周期长**【待验证】，比赛奖金不能当收入。验证期目标不应是「证明盈利」，而是「证明单条成本可控 + 至少 1 家机构愿意付一次钱」。

### 4. 决赛答辩预演：5 个致命问题与高分应对

应对总原则：**先承认现状 → 给出证据 → 给出日期**；绝不把 demo 表述外推为生产性能（团队已自列诚实红线）。

| # | 评委发难 | 高分应对 |
|---|---|---|
| 1 | 「有真实长者用过吗？还是你们自己演的？」 | 直接承认唯一故事为角色扮演、已逐字标注；展示真实采集排期（社区伙伴、同意书、日期）与已完成的第一段真实录音（若届时已有）。绝不含糊「已有用户」。 |
| 2 | 「和 Whisper + ChatGPT 有什么区别？」 | 不讲模型名，讲可验证链路：原音不替换、逐词置信度可视化、时间戳出处可回放、无命中即拒答、口语用字保真（Whisper 会把「嘅/唔」改成书面语，等于篡改史料）。现场点一个词跳播原音。 |
| 3 | 「谁付钱？付多少？」 | 讲清三层漏斗与买方-操作者-讲述者拆分；展示已签 LOI / 已接触机构清单，没有就明说「这是待验证假设，验证动作是 X，负责人 Y，日期 Z」；把 TAM/SAM/SOM 的每个乘数标出来源。 |
| 4 | 「80 岁长者怎么用这个 App？」 | 承认原设计不成立；现场演示重构后的双人协同采录：青年持机、长者只说话，问题卡片引导，长者无需注册、无需看地图。把「把手机塞给长者」变成「我们改过的设计」。 |
| 5 | 「四级隐私和撤回权怎么落地？服务器在哪？」 | 承认目前仅界面、无服务端过滤，且 consent 文案与实际持久化不一致已列为必修项；给出服务端过滤 + 删除日志 + 跨境/保留期说明的交付日期。此题撒谎代价最大，因为评委可能当场点「我的」页看到「準備中」。 |

加分动作：主动讲「我们拒绝过的东西」——语音克隆/TTS、社交 feed/点赞——把红线变成 Trusted AI 的信任资产（文档与 OmniWatch AI 先例同逻辑）。

### 5. 6 周验证期里程碑（建议作为投资/晋级的 gate）

| 周次 | 交付 | 达标证据 |
|---|---|---|
| W1–2 | 修诚实性与合规债 | consent 文案与实际存储一致；删除日志；服务端隐私过滤一条路径打通 |
