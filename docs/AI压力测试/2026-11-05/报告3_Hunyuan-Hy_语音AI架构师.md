## 模型输出全文

### 0. 架构评审前置校正

在回答三问前必须校正背景，否则方案会建在错误的地基上：

1. 后端实际路由是 `POST /api/process`（`server.py:58`），不是 `/transcribe`；它接收上传音频做一次性 STT + Gemini 结构化，**不落盘、不返回 record id**。
2. 「村口问答」目前**不是 RAG**：`KEYWORD_GROUPS` + `retrieveSegments()` 在客户端做字符串包含匹配，拼接命中段落并附 `Source: [YL-001] at mm:ss`；无命中即拒答。审计已确认「client-side keyword/bigram matching, not vector search」。
3. 词级时间戳与置信度**已有**（`words[]{word,start,end,confidence}`），前端也有 Q&A 卡片跳轨，所以第 2 问是「工程稳定性」问题，不是「从零实现」。
4. 四级隐私只有 UI、无服务端过滤；无故事元数据（主题/年代/方言/隐私层级/标签）。这些缺失会直接卡住第 3 问。
5. 线上 `gemini_ready=false`，qa_list 为空；无 GEMINI_API_KEY 时降级为空结果。任何「LLM 自动分类」方案都要先解决密钥与降级策略。

**结论**：本项目真正的技术壁垒不该是「换一个更大的 ASR 模型」，而是**「可验证的时间轴 + 可治理的元数据 + 可审计的检索过滤」三件套**。这也正好对应 Google 文档末尾指派给 Zheng 的方案 4（故事细分与人工兜底）——它是 RAG 与地图动态化的地基，必须排在最前。

### 1. 本土方言识别突破：先别急着 LoRA

**为什么不把 Whisper LoRA 当第一步**：Whisper 在粤语上会把口语用字改写成普通话书面语（「嘅/唔/呢」→「的/不/這」）。对口述史档案而言，**改写用词等于篡改史料**，直接违反诚实性红线。用会改写口语的模型做主干，再用后处理「修回粤语」，成本高于收益且不可验证。因此微调只能作为 Phase 2 的候选，且必须建立在「原音 + 原始逐字稿不替换」的前提上。

**有限预算下的三层路径（按 ROI 排序）**

- **L1 · 方言语料与评测先行（最高优先，Boris 现有工作即可扩展）**
  - 建 3–5 段不同说话人/环境杂音的内部测试音频，人工黄金标准转录（内部保存，不上传公开 GitHub）；按「粤语 / 围头话词汇 / 客家口音 / 噪音 / 语速」分层。
  - 定义可公开口径的指标：WER / CER、**粤语口语用字保留率**、词级时间戳误差（ms）、低置信度召回率。没有这套口径，「识别率偏低」只是感觉，不能写进报告也不能支撑 ITF。
  - 产出 `eval/` 目录与一份 `model_card.md`，把 demo-scope 升级为 measured。
- **L2 · 词典 + 音素级对齐（低成本、见效快）**
  - 建「新界乡村术语表」：地名（古洞、新田、粉岭…）、围头话/客家话常用词、亲属称谓、农事与节庆词汇，人工收集 100–300 条即可起步。
  - 用 STT 的 `speech adaptation` / phrase hints 类能力注入术语（Google STT 是否支持 `yue-Hant-HK` 的自定义词汇与提升效果须实测【待验证】）；对识别错的低频词做**音素级对齐**（用 forced alignment 把音频片段与候选词对齐，只替换该片段的转写，不重写整句），保证原音与逐字稿一一对应。
  - 低置信度词保留原样并高亮标「机器猜测，未确认」，交由志愿者人工兜底——这延续了团队「不确定性可视化」原则，也是方案 4 的第二层。
- **L3 · 双引擎与 Offline-first（护城河 + 田野场景）**
  - 主引擎保留 Google STT `yue-Hant-HK`（成熟、有词级置信度与时间戳）；引入 SenseVoice 作为离线/降级引擎（开源、原生保留粤语口语用字、可端侧）。
  - 关键工程问题：两引擎的**置信度口径不一致**，不能直接比较。做法是把置信度归一到「三档：高 / 待确认 / 拒识」，并用 L1 的黄金集分别校准阈值【待验证】。
  - 价值：网络差的村落可离线采集、避免单一供应商依赖，同时是「本地化 + 可落地」的评委加分项。
- **L4 · LoRA 微调（Phase 2，条件触发）**
  - 触发条件：已有 ≥N 小时**带明确授权**（同意书须单独允许用于模型训练/评测，默认否）的真实方言语料 + L1 评测集 + 可复现训练脚本。
  - 微调对象优先考虑「保真型」目标（保留口语用字、方言词），而非「书面化」目标；训练前后必须在 L1 集上回归，口语用字保留率不得下降。
  - 没有授权数据前不要动微调：把长者声音用于训练属于新的使用目的，需另行同意（见报告 2 的 PDPO SOP）。

### 2. 毫秒级音文同步：单一时间源 + 索引 + 状态机

现有 `words[]{start,end,confidence}` 与 Q&A 的 `timestamp` 已经是同一条时间轴，问题在于播放器的事件抖动与多来源写冲突。目标架构：

**2.1 唯一真值**：`audio.currentTime` 是唯一时间源；严禁另设 `setInterval` 累加的「逻辑时钟」。所有 UI 高亮、字幕滚动、Q&A 卡片激活状态都由它派生。

**2.2 索引与查找**
- 预处理：把 `words[]` 按 `start` 排序、去重、修正重叠（相邻词 `end > next.start` 时取中点），构建 `starts[]` 前缀数组。
- 每帧用二分查找定位当前词索引 O(log n)，不要用线性扫描整个词表。
- Q&A 的 `timestamp` 与词级时间戳统一到「音频相对秒」；如音频经过裁剪/拼接，必须记录 `offset` 并在切分处重映射，否则出处会系统性偏移。

**2.3 渲染与节流**
- 用 `requestAnimationFrame` 驱动高亮，`timeupdate` 事件只作为「醒过来」的触发（浏览器触发频率通常不足以做流畅字幕）；页面不可见时暂停 rAF。
- 高亮更新做 dirty check：索引不变就不碰 DOM；长 transcripts 用虚拟列表/分段渲染。

**2.4 Seek 状态机（防抖动的核心）**
```
IDLE → SEEK_REQUESTED(词/卡片点击) → SEEKING(设置 currentTime，加锁)
     → 等 'seeked' → 回写基准时间 + 立即重算索引 → IDLE
```
- 连续点击时合并为最后一次请求，加锁期间忽略新的 seek 请求或做 100–150ms 防抖。
- `seeking` / `seeked` / `play` / `pause` / `ratechange` 都要纳入状态；`playbackRate` 变化、音频 `preload` 不足、移动端自动播放策略是常见抖动源。
- seek 到未缓冲位置时先显示「载入中」，不要立刻把字幕跳到错误位置。
- 点击单词与点击 Q&A 卡片走**同一个 seek 函数**，避免两套逻辑产生偏移。

**2.5 双向联动与验收**
- 正向：播放 → 高亮当前词 + 自动滚动 + 低置信度词特殊样式。
- 反向：点词 / 点 Q&A 时间戳 / 点引用 → seek 并播放，统一附 `Source: [storyId] at mm:ss`。
- 验收用例（可写成 `tools/` 下的自动化检查）：暂停/倍速/快速连点/切后台/长音频分块/低置信度词密集段落；指标为「高亮与音频偏差 < 100ms（具体阈值按设备实测）」与「连续 20 次 seek 无卡死」。

### 3. 时空知识图谱 RAG：先把检索池治理好，再谈图谱

**3.1 现状到目标的差距**：当前是「一张硬编码故事 + 关键词词表 + 字符串包含」。目标不是立刻上图数据库，而是先把**可检索单元与元数据**定义清楚。

**3.2 最小元数据 schema v0.1（这是文档末尾方案 4 的工程化版本）**
每条 `segment`（建议按语义/时间切分为 15–60 秒）带：
```
segment_id, story_id, audio_uri, start, end,
raw_text, formal_text, words_ref,
village, area, geo_fuzzy {lat, lng, radiusM},
era_or_year, topic_tags[], dialect, speaker_role,
confidence_min, llm_suggested {time, place, topics},
review_status {pending|auto|human_confirmed}, reviewer_id,
consent_scope {private|family|community|public}, sensitive_flags[],
source_citation, created_at, version
```
- `llm_suggested` 与 `review_status` 分开存放：LLM 给候选（第 1 层），志愿者确认或改写（第 2 层人工兜底）；**绝不让 LLM 输出直接成为可公开事实**。
- 这套 schema 同时服务：故事细分/归类（方案 4）、地图动态层（方案 2）、时空检索过滤、隐私过滤、以及未来开放元数据 federation（文档 P2 提案）。成本只是一份文档 + 一张表，是性价比最高的一步。

**3.3 检索链路（服务端，不在客户端）**
```
Query → 意图/关键词抽取 → 混合检索(向量 + BM25/关键词)
      → 硬过滤: consent_scope ⊆ 当前访客权限 + geo/era/topic 约束
      → 片段重排 → 只取已确认(human_confirmed 或高置信)片段
      → 用原文片段拼答案 + 必附 [story_id] at mm:ss 出处
      → 无命中 → 拒答「錄製故事中未包含此資訊」
```
- **隐私过滤必须在检索前**（server-side），因为四级隐私目前只有界面；把过滤放在前端等于没有过滤。
- 保持团队红线：答案只由已录制并授权的逐字稿组成，禁用外部知识；`formal_text` 只作阅读辅助，不作答案依据；LLM 负责「组织与拒绝」，不负责「生成史实」。
- 时空约束：`era_or_year` + `geo_fuzzy` 用于「1950 年代的粉岭」这类提问的过滤；模糊半径保持 800m，不下钻到门牌。

**3.4 与香港历史地图对齐**
- 数据层可对接公开地理/历史地图资料（团队文档提到 HK Map Service / GeoInfo Map；OSM 底图 license 审计已列为待办）。**具体数据集、使用条款、可否商用与署名要求全部【待验证】**，核实前只做 mock，不写进生产链路。
- 建议做一个「清拆时钟」数据抽象层：村落 → 发展范围/公开时间表 → 采集紧迫度，前端叠加为颜色层；**公开数据 + 村级模糊圈，不涉及个人位置**，不碰隐私红线。这也是文档末尾方案 2「升级地图让城市变化有动态感」最稳妥的实现方式：先做时间维度的静态数据层，再谈动画。
- 「知识图谱」本身可延后：在只有 1 则 demo 故事、0 则真实故事的规模下，上图数据库是过度工程。先做到「segment + 元数据 + 混合检索 + 可验证引用」，实体关系（人-地-事-时）作为 v0.2 增量。

**3.5 无幻觉保证的可验证性**
每次回答落一条审计记录：query、命中 segment_id 列表、过滤条件、出处时间戳、拒答原因。配合第 2 节的时间轴，评委可现场点出处跳回原音核对——这比任何「我们用了 RAG」的说法都更有说服力，也是报告 1 所说「可信性工程」护城河的技术落点。

## 模型间差异备注（对比其他模型时填写）

- 与 GPT / Claude / Gemini 版报告的差异：尚无该模型版本，待复测。
- 更优的点：以仓库真实路由与检索实现为起点，指出「Whisper LoRA 优先」会违反口语保真红线并给出替代路径；把方案 4 的元数据 schema 明确为 RAG 与地图动态层的共同地基；给出可写测试验收的 seek 状态机。
- 更差的点：未实测 Google STT `yue-Hant-HK` 的自定义词汇/语音适配效果、SenseVoice 置信度分布与香港历史地图数据许可，相关结论均标【待验证】；单模型单轮输出，未经跨模型技术对抗复核。
